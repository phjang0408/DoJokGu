# 첫 멀티플레이 프로토타입 준비 작업 현황

「족구하세요 개발 준비 계획서」를 기준으로 첫 멀티플레이 프로토타입과 캐릭터 공통 리그의 현재 상태를 기록한다. 2026-10-06 기준 경기 규칙·코트·이동·공격 코드와 12종 캐릭터 리그 및 Unreal 기본 연결이 준비되어 있다. 같은 날 작성한 네트 통과 기록과 클라이언트 공 표시 보간 코드는 2026-10-08에 빌드했고 자동 테스트 5개를 통과했다. 지연 환경 PIE 검증은 남아 있다(8절). 2026-10-08에 선수 5명 로스터와 CampusEnclosed 배경 맵(10절)을 연결했다. 2026-10-12에 경기 맵 대기 단계(선수 선택·준비), 학교 로비(`L_Campus_Lobby`), 설정 패널, 같은 와이파이 방 만들기·찾기를 만들었고 자동 테스트 6개를 통과했다(7·8·10절). 2026-10-14에 캠퍼스 보행 확인(사용자 PIE, 이상 없음)을 마치고, 로비 AI 학생·달리는 차·흐르는 강과 로비 스폰 위치 조정을 넣었다(8·10절). 같은 날 타격 거절 기록, 접속 실패 시 세션 정리, 선수 목록 에셋 통합(`DA_JGCharacterRoster`), 템플릿 코드·에셋 정리를 했다(1·7·8절). 2026-10-15에 멀티플랫폼 확장 순서(Windows → Android → 인터넷 크로스플레이 → iOS)를 정하고 Windows 패키징을 마쳤다. 그 과정에서 게임 빌드 실패, 나무 가지 UV 누락으로 인한 실행 멈춤, LAN 방이 검색되지 않던 세션 정원 버그를 고쳤다(11절). 남은 항목은 이 문서의 8~9절에 분리해 적는다.

## 2. 구현한 경기 규칙 (계획서 2절 결정 사항)

| 항목 | 현재 구현 |
| --- | --- |
| 승리/듀스 | 7점 이상 + 2점 차 (`TargetScore`, `WinMargin`) |
| 첫 서브 | Host가 무작위로 정해 GameState로 복제. 이후 득점자가 서브 |
| 서브 준비 | 1.5초 대기 → 서브 입력 허용, 10초 초과 시 상대 득점(`ServeTimeout`) |
| 서브 위치 | 자기 코트 네트에서 500cm 지점. 점수마다 위치·공·입력 저장·슬라이딩 상태 초기화 |
| 바운드 전 타격 | 허용. 받는 쪽 바운드는 최대 1회 |
| 자기 공 연속 타격 | 금지 (`CanTeamHit`: 기대 수신 팀만 칠 수 있음) |
| 라인 위 착지 | 인. 판정 사각형은 라인 바깥쪽 경계, 코트 선 메시는 경계 안쪽에 그린다 |
| 첫 착지 아웃 / 자기편 착지 | 친 사람 실점 (`OutOnFirstLanding`, `FailedToCross`) |
| 인 바운드 후 재접촉 | 위치 무관 받는 사람 실점 (`NotReturned`) |
| 네트 | 공은 네트에 튕기기만 한다. 넘어가지 못하고 자기편에 떨어지거나 멈추면 친 사람 실점. 네트 평면 통과 지점은 진단용으로만 기록한다 (빌드 검증 전) |
| 이동 영역 | 자기 코트 + 바깥 100cm. Pawn만 막는 보이지 않는 벽(공은 통과) |
| 정지 중 슬라이딩 | 마지막 유효 이동 방향, 없으면 상대 코트 방향 |
| 경기 중 이탈 | 경기 종료 + 남은 사람에게 "Opponent left" 표시. 새 플레이어가 오면 새 경기 |
| 득점 중복 방지 | 라운드당 `bPointResolvedThisRound` 1회 + 득점 후 공 랠리 상태 해제 |

## 3. 핵심 설계

- **Host 권한**: GameMode(서버)가 판정 → GameState의 `FJGMatchSnapshot` 하나로 복제 → Host는 직접, Client는 RepNotify로 같은 `OnMatchStateChanged` 호출 → HUD는 한 경로로 갱신.
- **공**: Sphere 루트 + ProjectileMovement (물리 시뮬레이션 없음). `JGBall` 전용 충돌 채널(기본 Ignore)이라 코트 바닥·네트만 공을 튕긴다. 캐릭터 몸과 충돌하지 않는다. 바닥은 `JGGround` 태그가 붙은 단일 박스라 중복 바운드가 없다.
- **공 표시 보간 (빌드 검증 전)**: 클라이언트는 서버 위치를 받으면 충돌체를 즉시 옮기고, `VisualMesh`만 이전 위치에서 약 0.08초(`VisualSmoothingTime`)에 걸쳐 따라가게 한다. 오차가 150cm(`VisualSnapDistance`)를 넘거나, 새 샷(ShotId 변경)이 시작되거나, 경기 진입·해제가 일어나면 즉시 맞춘다. 공 그림자도 보이는 공을 따라간다. Host는 서버이므로 보간하지 않는다.
- **네트 통과 기록 (빌드 검증 전)**: 서버가 매 틱 코트 좌표에서 공 중심이 네트 평면(X=0)을 받는 쪽 방향으로 처음 넘는 순간을 보간해 `FJGRallyState`의 `bCrossedNet`, `NetCrossingClearance`(공 아래쪽과 네트 위 사이의 높이 차이, 음수면 네트 접촉), `NetCrossingLateral`(좌우 위치)에 기록한다. 샷마다 한 번 기록하고 새 타격 때 초기화한다. 받는 사람이 넘어오기 전의 공을 치는 것은 합법이므로 득점 판정에는 쓰지 않고, 득점 로그·연습 모드 메시지·`jg.Debug.Draw 1` 표시(초록=통과, 빨강=네트 접촉)에만 쓴다.
- **타격**: 클라이언트는 손을 뗄 때 `FJGAttackInput`(종류·각도·파워)을 Server RPC로 한 번 보낸다. 서버는 150ms 입력 저장 슬롯에 넣고 매 틱 거리·높이·수신 차례를 검사해 한 번만 새 속도를 준다. AnimNotify는 판정에 쓰지 않는다.
- **궤적**: 드래그는 파워에 따라 수평/수직 속도를 Curve로 연속 보간 (코트 안 보정 없음). 탭은 네트 위 여유 높이를 지나 네트 뒤 150cm에 떨어지는 포물선을 해석적으로 푼다. 슬라이딩 성공은 높고 느린 반환(1.6초 비행).
- **모션 구간**: 약(<33%)/중/강(≥67%)은 몽타주 선택에만 쓰고 속도는 끊기지 않는다.
- **이동 제한**: `CanMoveNow`(서브 중 서브하는 쪽, 경기 종료, 슬라이딩 중)를 `JGCharacterMovementComponent::ConstrainInputAcceleration`에서 적용한다. 서버가 클라이언트 이동을 재현할 때도 같은 함수를 거치므로 규칙을 무시한 클라이언트는 서버 보정으로 되돌아간다.
- **슬라이딩**: Ready → Sliding(0.35초, RootMotionSource로 CharacterMovement 경유, 리치 확장) → Recovery(0.6초) → Ready.
- **카메라**: 코트가 팀별 카메라 위치를 계산 (각자 자기 코트가 화면 아래). 2026-10-08부터 각도 -42도·거리 2600cm·초점 네트 위(이전 -60도·1800cm·내 코트 150cm). 공 최고 높이 4.5m까지 19.5:9와 16:9 화면 위아래에 들어오도록 계산한 값이다. 좌우 추적은 데드존·비율·최대치로 제한.
- **공 표시**: 공 아래 지면 투영 그림자(높이에 따라 크기 변화)만 표시. 미래 낙하지점은 `jg.Debug.Draw 1`에서만 보인다.

## 5. 테스트 방법

1. **규칙 자동 테스트**: Session Frontend > Automation에서 `Jokgu` 필터 실행. 2026-10-12 `Jokgu.Rules.*` 5개(대기 단계 `WaitingRoom` 포함)와 `Jokgu.Shot.Calculator` 통과. 에디터 없이 `UnrealEditor-Cmd <uproject> -ExecCmds="Automation RunTests Jokgu;Quit" -unattended -nullrhi -DDC-ForceMemoryCache`로도 돌린다.
2. **두 명 경기 (PIE)**: `L_TestCourt` 또는 `L_Campus_Match` 열기 → Play 옵션에서 Number of Players = 2, Net Mode = Play As Listen Server → 실행. 양쪽에서 선수를 고르고 Ready → 서브 → 랠리 → 득점 → 듀스 → 재경기 흐름 확인.
3. **혼자 경기 흐름**: `BP_JGGameMode`의 `bAllowSoloMatch`를 켜고 1인 PIE.
4. **공 궤적 단독 테스트**: 월드 세팅 GameMode Override를 `BP_JGGameMode_Practice`로 바꾸면 `BP_JGBallLauncher`가 약/중/강/최대/탭을 3초마다 발사하고, 착지 판정이 화면에 표시된다. 콘솔 `jg.Debug.Draw 1`로 코트 영역·리치·예상 궤적 확인.
5. **로비 흐름 (PIE 1명)**: `L_Campus_Lobby` 열기 → 실행. Settings 패널, Play 패널(방 목록 검색) → Create room → `L_Campus_Match` 선택 화면 → Lobby 버튼 → 로비. 같은 와이파이 방 찾기·참가는 한 에디터의 PIE 두 개로는 확인되지 않으므로 기기 두 대(또는 PC 두 대)에서 확인한다.

## 8. 남은 작업 (코드)

- **캐릭터 능력치:** 선택 화면과 준비 단계는 10/12에 만들었다(7절). GDD 능력치 표가 오면 `DA_Char_*` 값만 바꾸면 된다(지금은 모두 3, 역할 설명 비어 있음).

- **PIE 검증 대기 (2026-10-06 코드 작성, 10-08 빌드·자동 테스트 통과):** 공 표시 보간과 네트 통과 기록(3절). 남은 확인은 다음과 같다.
  1. 2인 PIE에서 Network Emulation(약 100ms 왕복 지연)을 걸어 공이 끊기지 않는지, 새 샷에서 이전 궤적에 끌리지 않는지 본다.
  2. 득점 로그의 네트 여유 높이·좌우 위치가 실제와 맞는지 확인한다.

- **타격 거절 기록 (10/14 코드, 빌드·자동 테스트 통과, 실행 확인 전):** 서버가 실행하지 못한 공격 입력마다 `LogDoJokgu`에 `HitReject` 한 줄을 남긴다. 이유(단계, 슬라이딩, 타격 대기, 랠리 끝, 받을 차례 아님, 멀다, 낮다, 높다), 서버 공의 거리·높이, 요청 순간 클라이언트 화면의 공 거리·높이(`FJGAttackInput.ClientBallDistance/Height`, 진단 전용), 리치, 핑, 누적 거절 수를 적는다. 화면에서는 리치 안이었으면 `(IN REACH ON SCREEN)`이 붙는다. 약 100ms 지연 PIE에서 Output Log를 `HitReject`로 걸러 보면 된다. 이 표시가 자주 나오면 공 비행 시간·표시 지연·타격 허용 범위를 먼저 조정하고, 그래도 안 되면 과거 시점 검증을 검토한다(계획서 8절 5단계).

Host 쪽에서 상대 한 명이 끊긴 것은 실패로 보지 않는다(게임 모드 `Logout`이 경기를 끝내고 방은 새 상대를 기다림). 엔진 실패 이벤트는 PIE 창마다 따로 오므로 자기 GameInstance의 것만 처리한다. 방 만들기·참가 중 다시 누른 요청은 무시하고(`IsBusy`), 세션을 지우는 중에 또 지우라는 요청이 오면 순서대로 이어 붙인다. 앱 백그라운드 전환은 따로 처리하지 않는다: 돌아오지 않으면 연결 시간 초과(엔진 기본 60초)로 위 경로를 탄다.
- **모바일:** Android 패키징과 기준 기기 실측을 수행하고 LOD·메시 밀도·텍스처 및 모바일 렌더링을 조정한다. iOS 빌드·실기기 검증도 별도로 남아 있다. 순서와 담당은 11절.

### 알려진 제약

- Claude는 실행 중인 게임에 실제 키·터치 입력을 보내지 못한다(Slate 포커스 문제). 조작감·프레임 체감·발열은 사용자가 확인한다.

- 휴대폰이 Host가 되면 발열·배터리 부담이 크다. 크로스플레이에서는 PC Host를 우선한다.

- UI(모바일 점프 버튼, 화면 배치)는 요청 목록만 정리하고 제작은 사용자가 한다.

### 1단계 결과 (2026-10-15, Windows)

- 패키징: `RunUAT BuildCookRun -platform=Win64 -clientconfig=Development -build -cook -stage -pak -archive -archivedirectory=<프로젝트>/Saved/Packaged -nocompileeditor -UbtArgs=-MaxParallelActions=4`. 결과물은 `Saved/Packaged/Windows/DoJokgu.exe`(약 1.1GB). 넣을 맵은 `DefaultGame.ini`의 `MapsToCook`(로비·경기 맵)으로 지정했다. 처음 쿡은 셰이더 때문에 약 20분 걸리고, 두 번째부터는 `-iterate`로 바뀐 에셋만 쿡한다(약 1분). 첫 쿡이 끝난 뒤 쿡 프로세스가 종료 단계에서 멈춰(CPU 0) 강제 종료하고 `-skipcook -stage -pak -archive`로 이어 붙였다.
- 고친 것:
  1. `JGRigAnimationLibrary`: 몽타주 구간 추가·삭제는 에디터에만 있는 함수라 게임 빌드가 실패했다. `WITH_EDITOR`로 감쌌다.
  2. 나무 4종(`SM_DJG_Tree_A_ExportMesh_001/002`, `B_001`, `C_001`): 10/15에 붙인 가지 막대에 UV가 없어(전부 0) 쿡된 Lumen 카드 데이터에 NaN이 생기고, `Tree_B`는 범위값까지 NaN이 됐다. 실행 직후 Distance Field ensure가 터져 게임이 몇 분씩 멈췄다. `Art/Schoolyard/CampusEnclosed/fix_branch_uvs.py`로 가지 면에 박스 투영 UV를 넣고(백업 `DJG_CampusEnclosed_before_branch_uvs.blend`), `apply_tree_updates.py --meshes-only`로 메시만 다시 반영했다(맵은 손대지 않음). 다시 쿡하니 NaN 경고와 ensure가 사라졌다.
  3. **LAN 방이 검색되지 않던 버그**: 세션 정원을 상대 수(1)로 잡았는데, Listen Server에서는 Host 자신도 세션에 등록되어 빈자리를 하나 쓴다(`FOnlineSessionNull::RegisterPlayers`). 방을 열자마자 빈자리가 0이 되어 Host가 검색에 응답하지 않았다. 정원을 Host 포함 2명(`MatchPlayers`)으로 바꿨다. 8절의 "PIE 두 개가 서로의 방을 찾지 못함"도 이 버그 때문이었을 가능성이 높다.
- 개발용 콘솔 명령(Shipping 빌드에는 없음): `jg.Session.Host`(방 만들기), `jg.Session.FindAndJoin`(검색 후 첫 방에 참가). UI 없이 `DoJokgu.exe -windowed -ExecCmds="jg.Session.Host"`처럼 실행해 시험한다.
- 확인한 것(한 PC에서 패키지 창 3개): Host 창이 방을 만듦 → 두 번째 창이 LAN 검색에서 방 1개 발견 → 참가 → Host 로그 `Join succeeded`, 참가 창 경기 맵 입장. 방이 찬 뒤 세 번째 창의 검색 결과는 0개. IP 직접 접속(`open <IP>`)도 성공.
- 확인하지 못한 것: 실제 키 입력으로 하는 경기·재경기, PC 두 대 사이의 LAN 검색. 사용자가 PC 두 대에서 확인한다. 처음 실행할 때 Windows 방화벽 창에서 허용해야 방 검색·접속이 된다.
