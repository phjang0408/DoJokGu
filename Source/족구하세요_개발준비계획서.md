# 족구하세요 언리얼 개발 준비 계획서

**첫 목표는 캐릭터 1종과 임시 코트로 두 사람이 서브부터 재경기까지 끝낼 수 있는 모바일 버전이다.** 공의 거리 감각, 두 손가락 조작, Host와 Client의 타격 경험을 먼저 검증한 뒤 캐릭터 5종과 배경 연출을 붙인다.

이 계획은 「족구하세요 GDD」를 실제 작업 단위로 나눈 것이다. GDD의 탭 공격, 드래그 방향과 연속 파워, 원바운드, 슬라이딩, 친구와의 1대1 대전을 구현 대상으로 삼는다. GDD에 없는 세부 규칙과 수치는 아래에서 **제안** 또는 **초기 실험값**으로 구분했다.

일정은 **1인 개발, 주 20시간, 학습과 수정 시간 포함**을 가정한다. 첫 멀티플레이 프로토타입은 약 6~8주, Android와 iOS를 포함한 친구 테스트용 베타는 약 19주를 초기 예상으로 잡는다. 장비 확보 대기와 스토어 심사 기간은 포함하지 않는다. 실제 첫 2주 작업량을 보고 다시 산정한다.

## 1 완성 목표와 개발 순서

| 구분 | 포함할 결과 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 첫 멀티플레이 프로토타입 | 1종 캐릭터, 1개 코트, 이동, 탭과 드래그, 연속 파워, 임시 공격 동작, 짧은 입력 저장, 슬라이딩, 서브, 득점, 7점 경기와 듀스 | 같은 네트워크의 Android 두 기기에서 경기와 재경기를 완료하고 두 화면의 점수가 일치한다 |
| 인터넷 대전 버전 | 친구 방 생성과 참가, 준비 상태, 외부 네트워크 접속, 공 표시 보간, 접속 종료 처리 | 서로 다른 네트워크에서 양쪽이 번갈아 Host를 맡아 경기를 끝낸다 |
| 친구 테스트용 베타 | 캐릭터 5종과 능력치, 선택 화면, 최종 공격 동작, 카메라 조정, 사운드와 효과, 득점 연출, 감정표현, Android와 iOS 검증 | 기기 조합별 대전·재경기·퇴장과 성능 기준을 통과한다 |

개발의 중심 순서는 **공을 원하는 곳으로 보내기 → 이동하며 받아치기 → 두 기기에서 같은 경기 만들기 → 모바일 조작 다듬기 → 캐릭터와 연출 확장**이다. 다만 모바일 패키징과 인터넷 연결 가능성은 초반에 작은 실험으로 확인한다.

GDD에서 2차로 둔 입력 타이밍 보정은 최소 기능만 첫 프로토타입으로 당기는 것을 제안한다. 보정이 전혀 없으면 터치가 불편한 것과 경기 자체가 재미없는 것을 구분하기 어렵다. 부드러운 카메라 추적과 연출의 완성도는 이후에 높인다.

첫 프로토타입의 정식 상대는 사람이다. 혼자 개발할 때는 공을 반복 발사하는 테스트 장치를 사용한다. 이것을 정식 AI 대전 모드로 확장하지 않는다.


## 2 구현 전에 정할 경기 규칙

이 항목은 실제 코드를 쓰기 전에 한 번 정하고, 테스트 중 변경하면 기록한다. 특히 득점 원인을 먼저 정해야 공과 UI를 같은 기준으로 구현할 수 있다.

| 결정 항목 | 초기 구현 제안 | 이유 또는 확인할 점 |
| --- | --- | --- |
| 듀스 | 7점 이상이면서 2점 차일 때 승리한다. 점수 상한은 일단 두지 않는다 | 6대6 이후 7대6은 계속, 8대6은 종료로 검증한다 |
| 첫 서브 | Host가 무작위로 정하고 양쪽에 전달한다 | 이후 서브권은 GDD대로 득점자에게 간다 |
| 서브 준비 | 양쪽 준비 후 1.5초 대기하고 입력을 허용한다. 서브 제한시간은 우선 10초를 시험한다 | 시간 초과 시 상대 득점이라는 규칙도 함께 확정한다 |
| 서브 위치 | 각자 자기 코트 뒤쪽의 지정 지점에서 시작한다 | 점수마다 위치·공·입력 저장·수비 상태를 함께 초기화한다 |
| 바운드 전 타격 | 허용한다. 바운드는 0회 또는 1회 뒤 타격할 수 있다 | GDD의 ‘최대 1회’에 맞춰 시작한다 |
| 자기 공 연속 타격 | 자신이 찬 뒤 상대가 치기 전까지 다시 칠 수 없게 한다 | 네트 실패를 반복 터치로 무한히 살리는 상황을 막는다 |
| 라인에 떨어진 공 | 바닥 접점이 라인 바깥쪽 경계 위까지면 인으로 정한다 | 화면의 선과 판정용 사각형 경계를 일치시킨다 |
| 상대 코트 안에 한 번 튄 뒤 밖으로 나간 공 | 받는 사람이 다시 지면에 닿기 전에 살리지 못하면 받는 사람 실점 | 첫 착지부터 밖으로 나간 아웃과 구분한다 |
| 네트에 닿은 공 | 넘어가면 계속한다. 못 넘기고 자기편 바닥에 떨어지거나 정지하면 친 사람이 실점한다 | 네트 접촉만으로 즉시 득점하지 않는 방향이다 |
| 이동 영역과 몸 충돌 | 자기편 코트와 바깥 수비 여유 공간 1m 안에서 이동한다. 네트 반대편 진입은 막는다 | 초기에는 캐릭터 몸이 공을 튕기지 않고 별도 타격 판정만 공에 영향을 준다 |
| 정지 중 슬라이딩 | 마지막 유효 이동 방향을 사용한다. 아직 이동한 적이 없다면 상대 코트 방향을 사용한다 | 입력 방향이 0일 때 기술이 실패하거나 임의 방향으로 나가지 않게 한다 |
| 접속 종료와 앱 전환 | 첫 버전은 경기 중 이탈 시 경기를 종료하고 남은 사람에게 이유를 표시한다 | Host 교체와 진행 중 재접속은 후속 범위로 둔다 |

첨부 GDD 기준 수비 기술은 **슬라이딩**으로 계획한다. 헤딩으로 바꿀 경우에는 이름과 애니메이션뿐 아니라 이동 거리, 유효 높이, 입력 방식도 다시 설계해야 한다.

Android SDK와 NDK를 무조건 최신 버전으로 설치하기보다 엔진과 맞는 조합을 고른다. 버전별 요구사항은 [Epic의 Android 개발 요구사항](https://dev.epicgames.com/documentation/en-us/unreal-engine/android-development-requirements-for-unreal-engine)에서 확인한다. 스토어 제출용 요구사항은 실제 출시 준비 시점에 다시 확인한다.

### 실기기와 iOS 준비

처음에는 **Android 기기 2대와 데이터 통신 또는 서로 다른 Wi-Fi 환경**을 확보한다. 그중 한 대를 성능 기준 기기로 지정하고 기종, OS, 해상도, 주사율을 기록한다. PC 두 창 테스트는 빠른 개발용으로 계속 사용한다.

iOS까지 완성하려면 **Mac 접근 경로, 대응하는 Xcode, Apple 개발자 계정과 서명 설정, iPhone 실기기**가 필요하다. C++ 기반 프로젝트이므로 Windows 작업과 Mac 빌드를 연결하는 경로를 초반에 확인한다. 첫 4주 안에 빈 프로젝트라도 iPhone에서 실행해 본다. [Epic의 Remote Mac Builds](https://dev.epicgames.com/documentation/en-us/unreal-engine/creating-remote-builds-of-unreal-engine-projects-for-ios)

Android와 iPhone 간 대전을 검증할 iPhone 1대를 우선 확보하고, iOS끼리의 대전은 두 번째 iPhone을 빌리거나 테스트 참여자와 확인한다. 장비를 아직 구하지 못했다면 iOS 완료 시점을 따로 관리한다.

비용은 먼저 자산 구매에 쓰기보다 테스트 기기와 Mac 사용 가능 여부를 확인하는 데 배정한다. 유료 모델·애니메이션·플러그인은 실제 호환성 시험 후 선택한다. 구매 전 기록할 항목은 가격, 대상 엔진과 플랫폼, 수정 가능 여부, 사용 범위, 원본 파일 제공 여부다.

## 4 언리얼 프로젝트 시작 설정과 파일 관리

### 프로젝트 기본 방향

**Games의 Third Person C++ 템플릿을 출발점으로 제안한다.** 기본 캐릭터와 CharacterMovement를 활용하고, 이 게임에 맞는 높은 카메라와 터치 입력을 교체한다. 모바일 대상으로 만들고 퀄리티 프리셋은 Scalable 또는 해당 버전의 성능 지향 옵션을 선택한다.

화면은 가로형으로 잡고, 점프와 자유 카메라 회전 입력은 경기 조작에서 제거한다. 템플릿의 이동·카메라·터치 입력이 새 입력과 중복 실행되지 않는지도 확인한다.

단순한 코트와 미리 계산한 조명을 사용할 계획이라면 **Mobile Forward**를 첫 렌더링 후보로 삼는다. 고비용 조명 기능을 기본 전제로 삼지 않고, 그림자와 머티리얼은 기준 기기에서 확인하면서 추가한다. 성능 지향 프리셋 선택만으로 최적화가 끝나는 것은 아니다. [Epic의 모바일 렌더링 모드](https://dev.epicgames.com/documentation/en-us/unreal-engine/mobile-rendering-and-shading-modes-for-unreal-engine)

처음 활성화할 기능은 Enhanced Input과 현재 단계에서 실제 사용하는 모바일·온라인 기능으로 제한한다. GAS나 Game Features를 사용하는 구체적인 요구가 생기면 별도로 검토한다.

### 파일을 나누는 기준

아래 이름은 생성할 파일의 제안이다. 모든 클래스를 첫날 만들 필요는 없고, 해당 기능을 구현할 때 추가한다.

| 경로 제안 | 넣을 내용 |
| --- | --- |
| Content/Jokgu/Maps | L_TestCourt, L_MainMenu, L_Match |
| Content/Jokgu/Characters | 캐릭터 BP, 스켈레탈 메시, 공통 Animation Blueprint |
| Content/Jokgu/Gameplay | 공, 코트, 네트, 테스트용 공 발사 장치 |
| Content/Jokgu/Input | IA_Move, IMC_Match, PC 테스트 입력 에셋 |
| Content/Jokgu/UI | 경기 HUD, 공격 터치 영역, 로비, 결과 화면 |
| Content/Jokgu/Data | 경기 규칙, 공 궤적 Curve, 캐릭터 능력치 Data Asset |
| Content/Jokgu/Art 및 Audio | 공통 머티리얼, 배경, 이펙트, 사운드 |
| Source/Jokgu/Core 및 Gameplay | 경기 진행, 판정, 공과 타격 로직 |
| Source/Jokgu/Player 및 Online | 플레이어 입력, 상태, 접속 관리 |
| Docs | 결정한 규칙, 초기 수치, 작업 목록, 테스트 결과 |

Git에는 Source, Config, Content, 프로젝트 파일과 필요한 플러그인 원본을 관리한다. 생성되는 Binaries, Intermediate, DerivedDataCache, 일반 실행 로그는 기본적으로 제외한다. 외부 바이너리 플러그인은 공급사의 배포 구조에 맞춰 예외를 정한다. 인증서와 서명 키도 프로젝트 소스와 분리한다.

한 작업이 끝날 때마다 “드래그 파워 연속 적용”, “두 번째 바운드 득점 수정”처럼 기능 단위로 커밋한다. 매주 실행 가능한 패키지 한 개와 30초 내외의 플레이 영상을 남긴다. 에디터에서만 실행되는 상태를 오래 유지하지 않는다.

## 5 언리얼 클래스별 책임

**경기 결과는 Host가 결정하고, GameState는 그 결과를 모두에게 전달한다.** UI와 카메라는 각 기기에서 자기 플레이어에게 맞게 표시한다. Unreal의 네트워크 게임은 클라이언트·서버 구조이며, Listen Server는 Host가 플레이어이자 서버인 방식이다. [Epic의 Networking Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine)

| 구현 제안 | 맡길 일 | 중요한 경계 |
| --- | --- | --- |
| AJGGameModeBase | 참가 인원, 스폰, 서브권, 랠리 종료, 득점, 승리 판정 | 서버에서 경기 규칙을 실행한다 |
| AJGGameStateBase | 양쪽 점수, 경기 단계, 서브권, 라운드 번호, 단계 종료 시각 | 모두가 알아야 하는 경기 상태를 복제한다 |
| AJGPlayerState | TeamId, CharacterId, 준비 여부 | 상대도 알아야 하는 플레이어 정보를 담는다 |
| AJGPlayerController | 로컬 입력 연결, HUD 생성, 카메라 설정, 서버 요청 입구 | UI는 로컬 컨트롤러에서 만든다 |
| AJGCharacter | 이동, 슬라이딩 상태, 타격 요청, 애니메이션 | CharacterMovement로 이동한다. 판정은 서버에서 검증한다 |
| AJGBall | 공 이동, 충돌 정보, 마지막 타격자, 샷 식별자 | 공의 정답 위치와 접촉은 서버가 관리한다 |
| AJGCourt | 코트 경계, 네트 위치와 높이, 서브 지점 | 배경 메시와 독립된 수치로 판정한다 |
| UJGSessionSubsystem | 방 생성, 검색·초대 기반 참가, 접속 실패, 세션 종료 | GameInstance 수명에 맞춰 관리하며 경기 점수를 보관하지 않는다 |
| UJGBalanceData 및 UJGCharacterData | 궤적·이동·보정 수치와 캐릭터별 데이터 | BP나 코드 여러 곳에 동일한 숫자를 흩어 놓지 않는다 |

GameModeBase와 GameStateBase를 한 쌍으로 사용하고 별도의 경기 단계 enum을 둔다. 예를 들어 WaitingPlayers, PreparingServe, Serving, Rally, PointEnd, MatchEnd를 사용한다. 상태마다 허용할 입력과 종료 조건을 함께 정의한다.

처음에는 Character 안에 타격 함수를 두어도 된다. 코드가 커지면 입력 저장·타격 가능 여부·수비 상태를 묶어 HitComponent로 분리한다. 기능보다 먼저 큰 프레임워크를 만들 필요는 없다.

C++에는 판정, 상태 전환, 네트워크 요청, 반복 사용하는 계산을 둔다. BP와 에셋에는 외형, 수치 연결, UI 배치, 애니메이션과 연출을 둔다. 점수를 올리는 동일한 로직이 BP와 C++ 양쪽에 생기지 않게 한다.

## 6 공과 타격을 만드는 구체적인 순서

### 공은 제어 가능한 포물선으로 시작한다

첫 구현은 **Sphere Collision을 루트로 둔 공 Actor와 ProjectileMovementComponent**를 제안한다. 공의 초기 속도, 중력, 바운스를 조절하기 쉽고 단순한 코트에서 동작을 관찰하기 좋다. Simulate Physics를 동시에 켜서 이동 주체가 바뀌지 않게 한다. 이 컴포넌트는 바운스와 이동 보간 기능을 제공하지만 멀티플레이 타격 판정을 자동으로 해결하지는 않는다. [Epic의 ProjectileMovementComponent API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UProjectileMovementComponent)

다음 작업을 순서대로 수행한다.

1. 임시 공을 일정한 위치에서 발사하고 바닥에서 한 번 튀게 만든다.
2. 코트와 네트 충돌을 나누고, 바닥 충돌 때만 바운드 횟수를 세게 한다.
3. 캐릭터 없이 약한 공·중간 공·강한 공을 반복 발사하여 궤적을 비교한다.
4. 캐릭터의 타격 가능 범위와 높이를 표시하고, 유효한 공에 한 번만 새 속도를 준다.
5. 공격 종류와 파워에 따라 공의 초기 속도를 만드는 공통 함수를 연결한다.
6. Host에서만 충돌과 득점을 확정하고 Client의 공 표시를 연결한다.

발이 공을 실제 물리 충돌로 밀어내는 방식은 첫 타격 모델로 사용하지 않는다. 판정용 범위에서 공을 확인한 뒤 새 속도를 주고, 발 모션을 그 시점에 맞춘다. 발 메시의 충돌과 별도 타격 함수가 모두 적용되는 이중 타격도 막는다.

충돌 설정은 공과 코트 바닥·네트 사이를 Block으로, 공과 캐릭터 몸 사이를 Ignore로 시작한다. 타격은 별도 범위 검사로 수행한다. 발판이나 장식용 배경이 공을 뜻밖에 튕기지 않도록 공과 충돌할 대상을 명시한다.

### 공격별 공 생성 규칙

| 공격 | 계산할 내용 | 유지해야 하는 GDD의 특성 |
| --- | --- | --- |
| 탭 | 제안으로 캐릭터의 좌우 위치를 기준으로 상대 네트 뒤 가까운 지점을 잡고 짧은 궤적을 만든다 | 별도 방향 조작 없이 짧게 떨어뜨린다 |
| 드래그 | 좌우 각도와 0~1 파워를 받아 수평 속도와 수직 속도 Curve를 적용한다 | 입력에 따라 속도와 거리가 연속적으로 변하고 네트 실패·아웃이 가능하다 |
| 슬라이딩 | 성공 시 상대 코트 중앙 부근으로 높고 느리게 보내는 기본 궤적을 만든다 | 별도 방향·파워 조작 없이 안전하게 반환한다 |
| 서브 | Serving 상태에서 같은 탭·드래그 해석을 사용한다 | 재생할 서브 애니메이션은 한 종류로 유지한다 |

드래그 파워는 데드존을 뺀 유효 드래그 길이를 최대 유효 길이로 나누고 0~1 사이로 제한해 얻는다. 거리 감각을 유지하려면 **계산된 낙하지점을 항상 코트 안으로 보정하는 처리를 드래그 공격에 넣지 않는다.** 타격 위치가 네트에 가깝거나 멀 때도 네트와 아웃 위험이 자연스럽게 달라져야 한다.

약·중·강 구간은 재생할 애니메이션만 선택한다. 예를 들어 45%와 65%가 같은 중 공격 모션을 사용하더라도 공의 속도와 거리는 달라져야 한다. 서브에서는 이 구간 선택을 건너뛰고 고정 서브 모션을 사용한다.

처음부터 하나의 파워에 대해 모든 위치에서 안전한 결과를 만들려고 하지 않는다. 앞·중간·뒤의 세 타격 위치에서 20%, 50%, 80%, 100%를 발사해 속도와 수직 속도 Curve를 조정한다. 플레이어는 높이를 직접 입력하지 않는다.

### 원바운드와 득점 판정

공에는 최소한 LastHitterTeam, ExpectedReceiverTeam, ReceiverBounceCount, HasLandedInReceiverCourt, ShotId를 기록한다. 마지막으로 찬 사람이 누구인지만 알아서는 모든 아웃 상황을 올바르게 처리할 수 없다.

서버의 접촉 처리 순서는 다음과 같이 잡는다.

1. 이미 득점이 확정된 라운드의 충돌이면 무시한다.
2. 바닥 착지라면 코트 좌표로 위치를 분류한다.
3. 상대 코트의 유효한 첫 착지 전이라면, 밖에 떨어진 공이나 넘어가지 못하고 자기편에 떨어진 공은 타격자 실점으로 처리한다.
4. 상대 코트 안의 첫 착지면 받는 쪽 바운드를 1로 기록한다.
5. 그 뒤 상대가 타격하기 전에 다시 바닥에 닿으면 위치와 관계없이 받는 쪽 실점으로 처리한다.
6. 합법적인 상대 타격이 성공하면 새 ShotId를 부여하고 다음 수신자와 바운드 정보를 초기화한다.
7. 득점 함수는 라운드당 한 번만 실행하고, 공 정지·점수 반영·서브 준비로 이어간다.

코트 밖으로 나간 것을 공중에서 곧바로 아웃 처리하지 않는다. 네트 통과는 네트 평면을 넘는 순간의 공 위치와 반지름을 함께 확인한다. 네트 메시의 모양이나 여러 바닥 타일의 중복 충돌이 판정을 바꾸지 않게 한다.

빠른 공이 프레임 사이에 네트나 타격 범위를 통과할 수 있으므로 이동 Sweep과 필요한 서브스텝을 시험한다. 클라이언트 화면의 프레임 수가 바운드 횟수나 경기 결과를 결정하게 하지 않는다.

## 7 터치 조작과 수비 및 카메라

### 입력은 기기별로 받고 실행 함수는 공유한다

PC에서는 Enhanced Input으로 이동과 공격 테스트 입력을 연결한다. 모바일에서는 왼쪽 조이스틱과 오른쪽 UMG 터치 영역에서 받은 값을 같은 이동·공격 함수로 전달한다.

Enhanced Input은 입력 값과 이벤트를 게임 함수에 연결하는 역할이다. 공격 버튼의 드래그 길이, 손가락 식별, 터치 취소는 별도로 설계해야 한다. [Epic의 Enhanced Input](https://dev.epicgames.com/documentation/en-us/unreal-engine/enhanced-input-in-unreal-engine)

| 입력 단계 | 구현할 동작 |
| --- | --- |
| 공격 영역을 누름 | 오른손 터치의 PointerId, 시작 좌표, 시작 시각을 저장한다 |
| 누른 채 이동 | 시작점 기준 이동량을 DPI가 보정된 좌표로 계산한다. 좌우 방향과 파워를 갱신하고 화살표를 표시한다 |
| 손을 뗌 | 짧은 시간·작은 이동이면 탭, 기준 이상 이동했으면 드래그 공격 요청을 한 번 보낸다 |
| 길게 누르기만 함 | 초기 제안으로 취소한다. 의도치 않은 드롭 공격이 나오는지 테스트해 조정한다 |
| 터치 취소 또는 앱 전환 | 화살표와 입력 저장을 지우고 눌린 상태가 남지 않게 한다 |

왼손과 오른손은 서로 다른 PointerId로 관리한다. 이동 중 공격을 시작하거나 공격 영역 밖으로 손가락을 끌고 나가도 입력이 끊기지 않는지 확인한다. 마우스 한 개로 터치를 흉내 낸 시험만으로 멀티터치 완료를 판단하지 않는다.

이동은 카메라의 전방과 오른쪽 방향을 바닥 평면에 투영해서 계산한다. 공격의 전방은 캐릭터가 순간적으로 바라보는 방향보다 **자기 코트에서 상대 코트로 향하는 방향**을 기준으로 잡는다. 각 플레이어 화면에서 오른쪽으로 조준했을 때 오른쪽으로 날아가도록 좌표 변환을 따로 검증한다.

화살표는 GDD대로 캐릭터를 기준으로 표시한다. 방향은 보낼 좌우 방향, 길이는 파워를 나타내며, 화면에 보이는 화살표와 서버로 보내는 조준 값은 같은 계산 결과를 사용한다.

### 공격 입력 저장과 애니메이션

공격 확정은 손을 떼는 시점으로 제안한다. 확정된 공격 종류·방향·파워를 짧게 보관하고, 공이 유효한 범위와 높이에 들어오면 사용한다. 저장 슬롯은 한 개이며 새 입력은 이전 입력을 대체하고, 만료 시 지운다.

서버는 입력을 받았을 때 경기 상태, 수신 차례, 후딜레이, 거리, 높이, ShotId를 확인한다. 사용된 입력은 즉시 소모하여 같은 공에 두 번 적용하지 않는다. 득점·서브 전환·슬라이딩 시작 시에도 남은 일반 공격 입력을 정리한다.

애니메이션은 타격을 보기 좋게 표현한다. **클라이언트 AnimNotify만으로 실제 타격을 확정하지 않는다.** 서버가 정한 타격 시점에 판정을 수행하고, 공이 떠나는 순간과 발이 닿는 모션을 맞춘다. 약·중·강 모션의 선행 동작 길이가 다르면 입력 저장 시간과 함께 조정한다.

이 입력 저장은 모바일 조작 보정이다. 통신이 늦어 이미 지나간 공을 클라이언트에서 치기 어려운 문제는 8절의 네트워크 보정과 별도로 검증한다.

### 슬라이딩

슬라이딩은 Ready, Sliding, Recovery의 세 상태로 시작한다. 시작할 때 방향을 고정하고 일반 공격을 막는다. 유효 시간 안에 공을 살리면 안전한 반환 궤적을 한 번 적용한다. 실패했을 때도 후딜레이가 생기도록 한다.

이동은 서버가 승인한 수평 이동을 CharacterMovement 경로로 처리한다. 양쪽 기기가 제각각 SetActorLocation을 반복 호출하는 방식은 피한다. 첫 버전은 서버 승인 후 이동을 기준으로 만들고, 외부 네트워크에서 반응이 느리면 이동 예측 개선 작업을 따로 진행한다.

리치 범위를 넓히는 효과는 Sliding 상태에만 적용하고 Recovery에서는 원래 값으로 되돌린다. 슬라이딩이 성공할 때마다 일반 공격보다 유리해진다면 거리를 줄이기보다 먼저 반환 공의 높이·속도와 후딜레이를 조정한다.

### 카메라와 공 표시

처음에는 약 60도 하향의 고정 카메라에서 코트와 상대가 모두 보이게 만든다. 그다음 GDD의 좌우 부드러운 추적을 추가한다. 양쪽 모두 자신이 화면 아래쪽 코트를 쓰도록 각자 카메라 방향을 설정하는 것을 제안한다.

이동에 따라 카메라가 지나치게 흔들리지 않도록 추적 한계와 완충 영역을 둔다. 16대9와 긴 가로 화면에서 코트 양 끝, 조이스틱, 공격 버튼, 점수 UI가 겹치지 않는지 확인한다.

공 아래 표시하는 것은 **현재 공의 지면 투영 위치와 높이 단서**다. 미래 낙하지점 표시는 게임 HUD에 만들지 않는다. 개발용 궤적과 낙하지점 표시는 별도 Debug 옵션에서만 사용한다.

## 8 멀티플레이 연결과 동기화 계획

### 방에 접속하는 기능과 경기 복제를 구분한다

친구가 같은 방에 들어오는 기능과 공·점수가 일치하는 기능은 따로 완성해야 한다. 한 기기에서 두 창을 띄워 랠리가 되는 것, 같은 Wi-Fi의 두 기기가 접속하는 것, 서로 다른 네트워크에서 방에 들어오는 것을 별도 완료 항목으로 둔다.

GDD의 P2P 방향은 **Listen Server로 경기 권한을 Host에 두고, 접속에는 P2P 통신 경로를 사용하는 구조**로 해석한다. 양쪽 기기가 동등하게 점수를 확정하는 구조로 만들지 않는다.

EOS를 우선 검토하는 이유는 Unreal의 온라인 하위 시스템 연결과 플레이어가 호스팅하는 경기를 위한 P2P 소켓 설정을 제공하기 때문이다. 실제 모바일 로그인·패키징·기기 간 연결은 별도 실험으로 확인한다. 엔진 버전에 맞는 NetDriver와 설정을 사용하고, 다른 버전의 설정을 그대로 섞지 않는다. [Epic의 Online Subsystem EOS Plugin](https://dev.epicgames.com/documentation/en-us/unreal-engine/online-subsystem-eos-plugin-in-unreal-engine)

인터넷 연결에는 로그인, 방 정보 조회와 참가, 실제 게임 패킷 전달이 필요하다. NAT 환경과 직접 연결이 어려운 경우의 릴레이 경로까지 확인한다. “P2P니까 방 서비스나 중계 경로를 전혀 준비하지 않아도 된다”는 전제로 일정을 잡지 않는다.

### 초반에 끝낼 작은 연결 실험

게임 내용이 없는 최소 맵에서 다음을 확인한다. 이 실험은 전체 온라인 구현에 앞서 0단계에서 수행한다.

- 선택한 엔진과 EOS 구성으로 Android 패키지를 만들 수 있다.
- 서로 다른 테스트 사용자로 로그인하고, 한 명이 만든 방에 다른 사람이 들어온다.
- 서로 다른 네트워크에서 캐릭터 하나의 이동을 상대가 본다.
- Host와 Client 역할을 바꿔도 연결된다.
- 앱 종료 후 다시 방을 만들 수 있고, 실패 사유를 로그에서 찾을 수 있다.

처음 8시간 안에 완료하지 못하면 실패 단계를 “빌드, 로그인, 방 검색, 참가, 게임 통신” 중 어디인지 기록하고 해결 시간을 다시 산정한다. 확인되지 않은 상태로 온라인 구현을 완료 처리하지 않는다.

방 참가 UI는 우선 테스트 친구 목록 또는 시험용 방 목록으로 만든다. 최종 UX를 짧은 방 코드로 정한다면 코드 발급, 중복 방지, 세션 조회와 만료 처리가 추가 작업임을 명시한다. GDD에 방 코드가 필수로 정해진 것은 아니므로 첫 연결 실험에 포함하지 않는다.

### 무엇을 어떻게 공유할지

| 항목 | 권한과 전달 방식 제안 | 클라이언트 역할 |
| --- | --- | --- |
| 이동 | CharacterMovement의 기본 네트워크 이동을 활용한다 | 자기 이동 입력을 처리하고 상대 이동을 표시한다 |
| 공격 요청 | 소유한 Character 또는 PlayerController에서 Server RPC를 호출한다 | 공격 종류, 방향, 파워, 입력 번호를 보낸다 |
| 공과 충돌 | Host가 공의 정답 상태와 충돌을 계산한다 | 서버 상태를 받아 공을 부드럽게 표시한다 |
| 바운드·아웃·점수 | Host만 판정하고 GameState의 결과를 복제한다 | 전달받은 상태로 점수와 안내를 갱신한다 |
| 캐릭터와 준비 상태 | 요청을 서버에서 검증하고 PlayerState에 반영한다 | 상대 선택과 준비 상태를 보여준다 |
| 감정표현 | 재생 종류와 시점을 전달하고 빈도를 제한한다 | 각자 애니메이션과 효과를 재생한다 |
| 경기 단계 | 단계와 종료 서버 시각을 복제한다 | 카운트다운과 입력 가능 여부를 표시한다 |

클라이언트가 소유하지 않은 공 Actor에 직접 Server RPC를 보내는 구조로 시작하지 않는다. 요청은 자기 플레이어 객체를 거쳐 서버로 전달한다.

드래그 중의 화살표는 로컬 표시로 처리한다. 매 프레임 Reliable RPC로 방향을 보내지 않고 공격 확정과 같은 실제 사건을 보낸다. 점수와 경기 상태는 지속 상태로 복제하고, 효과 재생 메시지가 누락되어도 최종 점수는 맞게 한다.

Host도 같은 타격 검사 함수를 통과하게 한다. RepNotify를 받은 Client와 서버에서 직접 값을 변경한 Host가 동일한 UI 갱신 함수를 사용할 수 있게 하여 Host 점수 표시가 빠지는 오류를 막는다.

### 빠른 공의 지연 문제를 해결하는 순서

1. 서버에서만 공을 이동시키고 기본 위치 복제로 양쪽 결과부터 맞춘다.
2. Client에 시각적 공 메시를 따로 두고, 시각·위치·속도·ShotId가 포함된 상태 갱신 사이를 보간한다.
3. 새 타격, 바운드, 서브 리셋 때 오래된 보간 정보를 정리해 이전 궤적이 새 궤적을 끌어당기지 않게 한다.
4. 실측 왕복 지연 약 100ms에서 “화면에서는 닿았는데 서버가 거절한 타격”을 기록한다.
5. 빈도가 높으면 공 비행 시간, 표시 지연, 타격 허용 범위를 먼저 조정한다. 그래도 해결되지 않으면 서버의 최근 공·플레이어 상태 기록으로 제한된 과거 시점 검증을 추가한다.

과거 시점 검증을 추가한다면 허용할 최대 보정 시간을 별도 수치로 제한하고, 클라이언트가 보낸 시각을 그대로 믿지 않는다. 같은 ShotId인지, 이미 다른 타격이나 득점이 확정됐는지 확인한다. 양쪽 물리 시뮬레이션을 독립적으로 돌리고 항상 같은 결과가 나올 것이라고 가정하지 않는다.

이 작업은 온라인 단계의 핵심이다. 위치 복제 옵션을 켜는 것만으로 완료 처리하지 않는다. 첫 버전에서 Host의 지연상 이점이 완전히 사라진다고 보장하지 않고, 역할을 교대하는 테스트로 차이를 확인한다.

### 방과 경기 수명

메뉴에서 연결 완료 후 로비의 CharacterId와 Ready를 서버에 보낸다. 두 명이 준비되면 경기로 이동하고, 두 플레이어의 맵 로딩과 스폰이 확인된 뒤 서브 준비 시간을 시작한다.

결과 화면에서는 양쪽 재경기 의사를 모으고 점수, ShotId, 서브, 위치, 후딜레이, 입력 저장을 초기화한다. 나가기와 접속 실패 경로에서는 세션 정리를 공통 함수로 모은다. Host 종료, 화면 잠금, 앱 백그라운드 전환, 통신 단절을 처리한 뒤 다시 방을 만들 수 있어야 한다.

## 9 필요한 에셋과 제작 순서

외형 제작은 **기준 캐릭터 1종에 이동과 킥을 적용하는 것**부터 시작한다. 생성형 이미지가 있다면 앞·옆·뒤 비율과 표정 방향을 정하는 참고자료로 쓰고, 게임용 메시·리깅·애니메이션 작업량을 별도로 잡는다.

| 자산 | 첫 프로토타입 | 베타까지 준비할 것 |
| --- | --- | --- |
| 캐릭터 메시 | 템플릿 캐릭터 또는 단순 임시 메시 1개 | 5종 외형 또는 1개 공통 몸체 기반의 실루엣·얼굴·의상 변형 |
| 스켈레톤과 리그 | 한 종류를 공통 기준으로 고정 | 체형이 달라도 공통 애니메이션이 무너지지 않게 검증 |
| 이동 애니메이션 | 대기와 달리기 | 옆걸음·후진이 필요한지 테스트 후 보완 |
| 공격 애니메이션 | 한 동작을 약·중·강 슬롯에 임시 연결 | 안축차기, 기본 발등차기, 큰 스윙 발등차기 |
| 서브와 수비 | 임시 서브, 임시 슬라이딩 | 고정 서브 1종, 슬라이딩 시작·진행·회복 |
| 감정표현 | 첫 버전에서는 생략 가능 | 도발·박수·좌절·자신감 중 공통 동작 4종 내외 |
| 공과 코트 | 공 1개, 평면, 직사각형 선, 네트용 박스 | 최종 공, 네트, 지지대, 경계선, 모래 또는 바닥 재질 |
| 배경 | 플레이 공간과 구분되는 단색 배경 | 학교 운동장 콘셉트라면 낮은 관중석·사열대·학교 외곽을 모듈로 제작 |
| 관중 | 정지 실루엣이나 단순 메시 | 적은 종류를 반복 배치하고 일부만 짧게 움직이게 한다 |
| UI | 점수, 조이스틱, 공격과 슬라이딩 버튼, 결과 | 캐릭터 선택, 준비 상태, 연결 오류, 감정표현, 화면 안전 영역 |
| 소리와 효과 | 킥·바운드·득점 구분용 임시음 | 강도별 킥, 네트, 슬라이딩, 휘슬, 관중 반응, UI 클릭과 소규모 먼지 효과 |

배경의 디테일과 관중 수를 늘리기 전 공, 공 그림자, 코트 선, 양쪽 캐릭터가 한눈에 구분되어야 한다. 관중과 배경은 매 프레임 개별 판단하는 Actor 수를 줄이고 반복 메시 배치를 활용한다.

외부 모델이나 애니메이션을 받을 때는 스케일, 정면 축, Root 뼈, 제자리 이동 여부, 리타게팅 결과, 머티리얼 슬롯 수를 확인한다. 강한 킥으로 캐릭터가 코트 밖으로 밀리거나 공통 리그에서 발이 지면 아래로 내려가는 문제를 기준 캐릭터에서 먼저 해결한다.

### 캐릭터 능력치 연결

김도윤을 기준 캐릭터로 두고 박준호, 최태성, 윤서진, 한재민은 GDD의 역할과 능력치 표를 유지한다. CharacterId로 데이터만 바꿀 수 있게 하고 캐릭터마다 별도 판정 코드를 만들지 않는다.

| GDD 능력치 | 연결할 실제 값 | 초기 조정 방향 |
| --- | --- | --- |
| 이동속도 | 최대 이동속도와 필요 시 가속도 | 3을 기준 100%로 두고 우선 작은 차이부터 적용한다 |
| 킥 파워 | 드래그 공격의 속도 Curve 배율 또는 최대 속도 | 공격력 수치가 아니라 공의 속도·거리 차이로 표현한다 |
| 정확도 | 서버가 타격 때 한 번 정하는 방향 편차 | 초기에는 편차 0으로 기본 조작을 검증한 후 작은 오차를 추가한다 |
| 리치 | 타격 가능 거리와 유효 높이 범위 | 보이는 발과 공 사이의 거리와 크게 어긋나지 않게 한다 |

배율의 첫 실험은 능력치 2, 3, 5에 대해 약 95%, 100%, 110% 수준을 제안한다. 정확도는 별도 오차 수치이므로 같은 배율을 그대로 적용하지 않는다. 무작위 방향 편차를 도입하면 서버가 한 번 정한 결과를 공유한다. 매 프레임 다른 난수를 넣지 않는다.

5종의 능력치 합계가 같다고 해서 실제 강함이 같아지지는 않는다. 이동속도와 리치는 공을 받을 기회 자체를 바꾸므로 실제 승률과 수비 성공 위치를 함께 본다.

## 10 밸런스 수치를 준비하는 방법

아래 숫자는 **정식 족구 규격이나 검증된 정답이 아닌 초기 실험값**이다. 캐릭터 크기와 화면에서의 체감에 맞춰 바꾼다. Unreal 안에서는 거리 단위를 cm로 통일한다.

| 항목 | 첫 실험값 또는 범위 | 조정 판단 |
| --- | --- | --- |
| 전체 코트 | 폭 800cm, 길이 1200cm | 혼자서 반 코트를 커버하는 데 걸리는 시간과 빈 공간이 생기는지 본다 |
| 네트 높이 | 100~110cm | 낮은 파워에서 실제 실패가 나오고 중간 파워로 랠리가 가능한지 본다 |
| 공 반지름 | 판정용 12~15cm | 가독성용 메시 크기를 별도로 조정할 때 판정과 차이를 확인한다 |
| 기본 이동속도 | 400~500cm/s | 상대가 좌우를 흔들 수 있지만 한 번의 공격으로 항상 끝나지는 않는지 본다 |
| 보통 공격의 반대편 첫 착지 시간 | 대략 0.8~1.4초를 탐색 | 앞·중간·뒤 타격 위치별로 도달 시간과 네트 높이를 함께 확인한다 |
| 드래그 방향 한계 | 상대 코트 전방 기준 좌우 35도 | 크로스 공격과 옆줄 아웃이 모두 발생하는지 본다 |
| 약·중·강 모션 경계 | 파워 약 33%, 67%에서 구분 | 모션만 바뀌고 경계 전후의 실제 공 속도는 끊기지 않아야 한다 |
| 탭 판별 | 180ms 이내, 작은 이동 | 실제 기기의 실수 탭·드래그 비율로 조정한다 |
| 드래그 기준 | UI 논리 좌표 12 정도를 데드존, 140 정도를 최대 길이 후보로 시험 | 실제 픽셀 수가 아니라 DPI가 보정된 위젯 좌표에서 계산한다 |
| 공격 입력 저장 | 150ms, 조정 범위 100~220ms | 미리 눌렀는데 씹히는지, 너무 늦게 자동 발동하는지 본다 |
| 일반 타격 리치 | 수평 100~140cm부터 시험 | 공 중심 높이에 대한 별도 유효 구간도 설정한다 |
| 탭 목표 깊이 | 상대 네트 뒤 약 150cm | 앞쪽 수비가 의미 있게 대응할 수 있는지 본다 |
| 슬라이딩 거리 | 약 200~300cm | 정상 이동으로 못 받을 공 일부만 살릴 수 있어야 한다 |
| 슬라이딩 유효 시간 | 약 0.3~0.4초 | 버튼 연타로 계속 넓은 범위를 유지하지 못해야 한다 |
| 슬라이딩 후딜레이 | 약 0.5~0.7초 | 안전 반환 이후 상대가 공격을 준비할 시간이 생겨야 한다 |
| 서브 준비와 득점 연출 | 각각 약 1.5초, 1초 | 짧은 경기에서 대기 시간이 지나치게 길어지지 않아야 한다 |

코트 크기와 이동속도를 먼저 정하고, 그다음 공의 속도·높이, 타격 범위, 입력 저장, 슬라이딩 순서로 조정한다. 한 번의 테스트에서 큰 변수는 하나나 둘만 바꾼다.

BalanceData와 Curve에 실제 값을 모으고, 테스트 기록에는 빌드 번호·기기·Host 역할·지연·바꾼 값·느낌·측정 결과를 남긴다. 서브 위치가 바뀌면 같은 파워의 결과도 달라지므로 타격 시작 위치를 함께 기록한다.

## 11 필요한 공부와 바로 만들 결과

이미 접해 본 Enhanced Input, GameMode, GameState, 델리게이트, CharacterMovement 개념을 이 프로젝트의 실제 기능으로 연결하는 방식으로 공부한다. 강의를 전부 끝낸 뒤 구현을 시작하는 계획으로 잡지 않는다.

| 순서 | 집중할 개념 | 공부 직후 만들어 확인할 것 |
| --- | --- | --- |
| 1 | 카메라 기준 방향, FVector2D 입력, AddMovementInput | 높은 카메라에서 화면 방향과 이동이 일치하는 캐릭터 |
| 2 | UMG 터치 이벤트, PointerId, 좌표와 DPI 변환 | 두 손가락으로 이동하면서 드래그 화살표를 조절하는 화면 |
| 3 | 초기 속도, 중력, Curve, Sweep과 충돌 이벤트 | 파워를 바꾸면 거리와 네트 통과 여부가 달라지는 공 |
| 4 | GameMode와 GameState, 상태 enum, 타이머 | 서브·랠리·득점·듀스·재경기가 이어지는 경기 |
| 5 | Actor 소유권, Server RPC, RepNotify, 서버 검증 | Client 공격으로 Host가 공을 움직이고 양쪽 점수가 맞는 장면 |
| 6 | Montage, Notify, 리타게팅, 상태 기반 애니메이션 | 서버 타격 순간과 발 모션이 맞고 수비 중 공격이 막히는 캐릭터 |
| 7 | 세션 수명, 로그인, NetDriver, 모바일 패키징, 지연 측정 | 서로 다른 네트워크의 실기기에서 한 경기 완료 |

온라인 연결의 작은 실험은 이 학습 순서와 별도로 초반에 수행한다. 표는 학습 깊이를 늘리는 순서이지 모든 접속 검증을 마지막까지 미루라는 뜻은 아니다.

하루 4시간 작업한다면 개념 확인 약 40분, 구현 약 2시간 20분, 실행 확인과 기록 약 1시간부터 시작한다. 막혔을 때는 현재 기능을 완성하는 데 필요한 API만 찾아보고, 실행 결과가 생긴 뒤 범위를 넓힌다.

## 12 단계별 작업량과 완료 기준

아래 시간은 외주 없이 기존 리소스를 일부 재사용하는 1인 개발의 초기 추정이다. 공부·구현·단계별 검증을 포함한 기본 작업량은 **300시간**, 통합 오류와 수정에 **75시간의 예비 시간**을 둔다. 주 20시간이면 약 19주다.

작업 단계는 의존성을 따라 진행하되, iOS의 첫 빌드는 7단계 작업 중 일부를 첫 4주 안에 앞당긴다. 표의 시간은 작업 묶음의 합계이며 그 선행 검증 시간을 중복으로 더하지 않는다.

| 단계 | 예상 시간 | 만들거나 준비할 결과 | 완료 기준 |
| --- | --- | --- | --- |
| 0 환경과 위험 확인 | 24시간 | 프로젝트와 Git, Android 첫 패키지, 테스트 기기 기준, EOS 최소 연결 실험, iOS 장비·계정 경로 | C++ 전체 빌드와 Android 실행. 외부 네트워크 빈 맵 접속 확인. iOS 확보 계획 기록 |
| 1 코트와 이동 | 24시간 | 임시 코트, 경계·서브 지점, 카메라, 이동, 조이스틱 | 양쪽 진영의 화면 방향이 맞고 모바일에서 코트와 공을 볼 수 있다 |
| 2 공과 공격 | 36시간 | 공 발사, 바운스, 타격 범위, 탭, 드래그, 연속 파워, 입력 저장, 임시 동작 | 위치와 파워별 궤적 차이, 네트 실패와 아웃, 이동 중 공격이 확인된다 |

| 4 인터넷 대전과 공 표시 | 48시간 | 실제 로비, 외부 접속 통합, 공 보간, 지연 시 타격 조정, 실패·퇴장·재접속 정리 | 외부 네트워크에서 Host 교대 경기 완료. 약 100ms 왕복 지연에서 타격 거절 원인 확인·수정 |
| 5 조작과 경기 피드백 | 32시간 | 터치 예외 처리, 카메라 추적, 최종 공격 동작 연결, 공 그림자, 득점 연출 | 서로 다른 화면비에서 조작이 안정적이고 타격·실점 이유를 구분할 수 있다 |
| 6 캐릭터와 아트 | 48시간 | 5종 외형과 데이터, 선택 화면, 배경, 기본 소리·효과·감정표현 | 모든 캐릭터가 같은 경기 흐름을 사용하고 구별 가능한 차이가 있다 |
| 7 iOS와 베타 통합 검증 | 48시간 | iOS 빌드, 기기 조합별 검증, 발열·프레임 조정, 연결 예외 수정, 배포 가능한 테스트 빌드 | Android끼리, iOS끼리, Android와 iOS 간 경기·재경기·퇴장 통과 |
| 수정 예비 시간 | 75시간 | 실기기·온라인 통합에서 드러난 문제 해결 | 남은 차단 오류가 없어 친구 테스트를 시작할 수 있다 |

3단계까지 기본 작업량은 124시간이다. 수정 여유를 포함해 첫 프로토타입을 약 120~160시간, 주 20시간 기준 약 6~8주로 본다. 캐릭터 5종을 각각 독립 모델과 독립 애니메이션으로 제작하면 6단계 추정은 크게 늘어나므로 별도 제작 계획이 필요하다.

일정이 늘어날 때는 관중 움직임, 감정표현 수, 장식용 이펙트, 캐릭터 외형 변형의 양부터 조정한다. 터치 조작, 공 판정, 외부 접속, 재경기, 목표 플랫폼 검증은 완료 기준에 남긴다. iOS나 5종 자체를 빼려면 GDD 범위 변경으로 따로 기록한다.

공개 매칭·랭크·재화·상점·진행 중 재접속·Host 교체·전용 서버·정식 AI 상대는 이 일정에 포함하지 않는다. 앱스토어 출시 자료와 심사 대응은 친구 베타를 검증한 뒤 별도 단계로 계획한다.

## 13 첫 일주일의 실제 작업

주 20시간을 다섯 번의 4시간 작업으로 나눈 예시다. 첫 주에는 임시 캐릭터로 시작하고, 실행 가능한 빌드와 가장 큰 접속 위험부터 확인한다.

| 작업일 | 할 일 | 끝나고 남길 결과 |
| --- | --- | --- |
| 1일차 | Third Person C++ 프로젝트 생성, 모바일·가로 화면 설정, C++ 전체 빌드, Git과 LFS 설정 | 최초 커밋과 재현 가능한 빌드 방법 |
| 2일차 | Android 도구 연결, 기기 설치, 패키지 실행, 간단한 프레임 확인 | 실기기 실행 영상과 엔진·SDK·기기 버전 기록 |
| 3일차 | EOS 시험 프로젝트와 테스트 사용자 준비, 로그인·방 생성·참가 확인 | 단계별 성공·실패 로그 |
| 4일차 | 다른 네트워크의 기기에서 빈 맵 이동 동기화, 역할 교대, 세션 종료 후 재생성 | 접속 실험 결과와 해결할 차단 항목 |
| 5일차 | 남은 환경 오류 정리, iOS 장비와 빌드 경로 확인, 2절의 규칙 결정 기록 | 결정한 규칙과 다음 주 작업 목록 |

첫 주의 연결 문제가 빨리 해결되면 L_TestCourt에 직사각형 바닥과 네트를 배치하고 높은 카메라를 만든다. 연결 실험이 막히면 아트 제작으로 넘어가기 전에 실패 단계를 좁힌다. 예정된 0단계 24시간 중 남은 4시간은 다음 작업 초반에 사용한다.

작업 카드에는 목적, 만들 파일·에셋, 완료 조건, 확인 방법, 남은 문제를 적는다. 예를 들어 “두 번째 바운드 득점” 카드의 완료 조건은 “상대 코트 안 첫 바운드 후 두 번째 지면 접촉에서 받는 사람만 실점하고 양쪽 화면 점수가 한 번만 오른다”로 쓴다.

## 14 검증 항목과 재미 판단

### 반복해서 확인할 기능

| 시험 | 합격 기준 제안 |
| --- | --- |
| 6대6 듀스 | 7대6은 계속하고 8대6에서 한 번만 경기 종료 |
| 첫 착지 아웃 | 마지막으로 친 사람이 실점 |
| 인 바운드 뒤 밖으로 이탈 | 두 번째 지면 접촉에서 받는 사람이 실점 |
| 네트 실패와 자기편 착지 | 판정이 멈추지 않고 올바른 사람에게 실점 처리 |
| 라인 경계 | 시각적인 코트 선과 판정 위치가 일치 |
| 연속 입력과 중복 충돌 | 한 입력은 한 번만 타격하고 한 랠리에서 점수가 중복 증가하지 않음 |
| 파워 45%와 65% | 같은 중 공격 모션에서도 실제 궤적 차이가 발생 |
| 앞·중간·뒤 타격 | 타격 위치가 바뀌어도 네트와 아웃 판정이 일관됨 |
| 멀티터치 | 이동하면서 탭·드래그·슬라이딩 가능. 손가락을 바꿔도 입력이 남지 않음 |
| 수비 상태 | 슬라이딩 중 일반 공격 불가. 종료 후 범위·속도·입력 상태 정상 복구 |
| 서브·재경기 | 입력 저장, 바운드, 공 보간, 점수, 위치, 후딜레이가 모두 초기화됨 |
| 중도 종료 | Host와 Client 각각 종료 시 남은 화면에 이유 표시. 메뉴에서 새 방 생성 가능 |

경기 승리 조건, 착지 위치 분류, 득점자 결정, 중복 득점 방지는 작은 자동 검사로 남길 가치가 있다. 터치감, 가독성, 발열, 지연 중의 플레이 감각은 실기기로 직접 검증한다.

### 네트워크와 성능

Unreal의 Network Emulation으로 지연과 손실을 주고, 패키지에서도 실제 네트워크를 확인한다. 설정값 자체를 왕복 지연으로 간주하지 말고 게임 안에서 측정한 RTT를 기록한다. 송수신 양쪽에 지연을 걸면 합산될 수 있다. [Epic의 Network Emulation](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-network-emulation-in-unreal-engine)

| 조건 | 확인할 결과 |
| --- | --- |
| 같은 네트워크, 지연이 적은 환경 | 10경기 동안 점수 불일치·중복 득점·랠리 멈춤 0건 |
| 왕복 지연 약 100ms, 손실 1% 수준 | 기본 랠리 가능. 화면상 접촉과 서버 타격 결과가 어긋난 사건을 기록하고 반복 원인 제거 |
| 왕복 지연 약 200ms, 지연 변동 약 20ms, 손실 3% 수준 | 조작감이 나빠져도 점수 불일치나 무한 대기 없이 경기·종료 처리 |
| Wi-Fi와 모바일 데이터 조합 | 양쪽 Host 역할에서 연결·경기·재경기·퇴장 |
| 앱 백그라운드·화면 잠금·강제 종료 | 입력이 고정되거나 상대가 무한 대기하지 않음 |
| 기준 기기 20분 연속 경기 | 60FPS 목표. 초기 허용 기준은 준비 구간 이후 프레임 시간 95백분위 20ms 이하로 제안 |
| 낮은 성능 기기의 보조 설정 | 필요 시 30FPS 설정 제공. 물리와 경기 규칙이 프레임 수에 따라 달라지지 않음 |

관중, 그림자, 먼지 효과, UI를 순서대로 켜며 어느 요소가 프레임에 영향을 주는지 본다. Host는 경기 처리와 화면 렌더링을 함께 하므로 Client 역할 때보다 부하가 커지는지도 측정한다.

### 공을 주고받는 재미의 판단

3단계가 끝나면 지인 2~4명과 짧게 테스트한다. 처음 5분은 설명을 최소화하고 “짧게 넘기기, 깊게 보내기, 좌우 빈 공간 공략”을 각각 시도하게 한다. 이후 잘 이해되지 않은 조작만 설명한다.

기록할 값은 평균 랠리 타격 수, 네트·아웃·수비 실패 비율, 탭과 드래그 사용 비율, 슬라이딩 시도와 성공 횟수다. 무조건 랠리를 길게 만드는 것이 목표는 아니다. 플레이어가 상대 위치를 보고 다른 선택을 할 수 있는지 함께 본다.

다음 현상이 반복되면 해당 문제를 먼저 수정한다.

- 누구나 강한 공격만 사용하면 탭의 거리·회복 시간과 강한 공격의 아웃 위험을 비교한다.
- 안전한 공만 중앙으로 보내면 이동속도, 코트 폭, 좌우 공격 각도를 비교한다.
- 슬라이딩이 매번 최선이면 후딜레이와 반환 궤적을 조정한다.
- 정확도 능력치 때문에 실수가 억울하게 느껴지면 무작위 오차를 줄인다.
- 처음 배운 사람 대부분이 타격에 실패하면 공 속도를 낮추고 입력 저장과 타격 높이 범위를 확인한다.
- Client만 지속적으로 놓치면 캐릭터 밸런스를 바꾸기 전에 네트워크의 표시 지연과 판정 시점을 확인한다.

첫 프로토타입의 통과 기준은 “모든 기능이 존재한다”에서 끝나지 않는다. **두 사람이 한 경기를 끝내고, 실점 이유를 이해하며, 다음 공격을 다르게 선택할 수 있어야 한다.** 이 상태가 확인되면 캐릭터와 배경 제작에 시간을 늘린다.
